LLM 基础（二）：LLM 能做什么？从「会生成」到「会做事」的能力地图

2026-10-29 #Agent#LLM#能力边界#模型选型#评估

上一篇 LLM 开发（一）：LLM 是什么？从预测下一个 token 到 OpenAI / Anthropic 协议 把模型拆成了一个函数：给定上下文，输出词表上的概率分布。也讲了它为什么会一本正经地胡说，以及那个 POST /v1/chat/completions 里每个字段在干什么。

这一篇回答下一个问题：那它到底能干什么？

这个问题看着像科普，其实是工程里最容易亏钱的一问。因为「能做什么」在 demo 里和在线上完全是两件事：

  • demo 里，它写了一段能跑的代码；
  • 线上，它有 3% 的概率把字段名写成一个不存在的 API，而这 3% 落在 10 万笔订单上。

所以这篇不打算列「100 个 AI 应用场景」。我想给你一把尺子：拿到一个需求，十分钟内判断出它落在哪一级、靠什么保证、错了怎么办、值不值得做。

1. 先拆掉一个误会：它没有手

所有「AI 帮我订了机票」「AI 自己修好了 bug」的演示，底下都是同一条流水线：

模型从头到尾只做了一件事：生成 token。它没有网络、没有文件系统、没有数据库连接，也没有「执行」这个动作。所谓「会做事」，是你写了一个函数，然后让模型来按按钮。

这句话有两个直接推论，贯穿整章：

  1. 能力上限由「你能不能把这个动作写成一个函数」决定。法律不允许、API 不存在、权限给不了，模型再强也做不到。
  2. 可靠性下限由「模型生成的这段意图对不对」决定。而这段意图，恰好是可以被校验的——这就是它能工程化的根本原因。

所以「LLM 能做什么」更准确的问法是：

它能稳定生成什么形状的输出？以及这个形状能不能被验证？

把这两个问题画成两个轴，就得到了本章的地图：

输出形状稳定 输出形状不稳定
可自动验证 分类、抽取、SQL、工具参数 → 直接上 代码、配置、正则 → 跑测试再上
不可自动验证 翻译、改写、短摘要 → 抽检上线 文案、方案、长文分析 → 人审，或者别用

很多团队的坑，是把右下角的任务当成左上角的任务来做：用一个开放式的 prompt，期待一个可验证的结果，然后用「感觉还行」来验收。这一格能不能成，基本看运气。

2. 所有能力都长在四种动作上

剥掉业务外壳，任何一次 LLM 调用的输入输出，都逃不出这四种：

动作 输入 → 输出 输出空间 可靠性 典型场景
变换 Transform 文本 → 同构文本 大，但语义等价 中高 翻译、改写、润色、格式转换
抽取 Extract 非结构化 → 结构化 小（schema 定死） 最高 分类、打标、字段抽取、实体识别
生成 Generate 少量输入 → 大量新内容 开放 中低 文案、方案、代码、长文
决策 Decide 上下文 → 一个选择 小（枚举） 中高 路由、是否退款、下一步调什么工具

顺带说一句：多模态不改变「四种动作」的划分。 图片被切成 patch，音频被切成帧，最后都变成同一串向量喂进 Transformer。所以「看图」本质上还是抽取和判断——它能描述图里有什么，但不能可靠地数图里有几个人，也读不清 4pt 的小字。原因和它在 strawberry 里数不清 r 是同一个：tokenizer 根本不给你那个粒度。

为什么可靠性是这么排的？因为输出空间越窄，模型越不容易跑偏，你也越容易验证。

  • 抽取的候选空间是 schema 定义的有限结构，JSON Schema 一校验就知道对不对；
  • 决策的候选空间是一个枚举，可以用 logprob 算置信度（上一篇 4.3.2 那段）；
  • 变换的候选空间是「同一个意思的另一种说法」，可以回译、可以比对关键实体；
  • 生成的候选空间是开放的——你没法枚举「一篇好文案」的所有可能，也就没法写验证器。

这里有个很现实的规律：商业价值和可靠性往往是反着来的。 越像「智能」的任务（写方案、做诊断、给建议）越值钱，也越难验证；越能被 schema 锁死的任务（分类、抽取），越稳，但越像传统软件。

但这不意味着「所有任务都压成抽取」。真实系统分两层，很多人只做了「把输出锁死」这一层，所以模型一遇到多步任务就崩。

2.1 任务级：先规划，再执行

复杂任务不要指望一次生成就对。正确的做法是让模型先把任务拆成计划，再按计划一步步执行：

为什么必须先规划？因为一次生成里，模型能看到的只有自己写出来的 token，看不到工具的真实返回。它只能靠想象把 10 步全推完，然后一次性写出来——这正是上一篇说的滚雪球：第 1 步猜错，后面 9 步都在为错误圆场。规划把任务切成多个回合，每个回合结束后都能拿到真实观察，再决定下一步；错误因此有机会被挡在下一步之前。

三个字段值得单独说：

  • action 必须是工具清单里真实存在的，否则就是计划幻觉；
  • args 要过 schema 校验，别让模型编出不存在的参数；
  • done_when 是这一步的验收条件——没有验收条件的步骤，等于没有终点。

计划也不是一次定死的。执行到第 2 步发现「女装没异常，母婴才异常」，就应该改计划。这就是 Plan-and-Execute 和 ReAct 的分界：先规划降低盲目探索，边执行边观察防止计划脱离现实。

但规划不是银弹。规划本身就是一次生成，而且是开放度很高的生成，所以它同样会犯四种错：

规划失败 症状 怎么兜
工具幻觉 计划里出现不存在的工具或参数 用工具清单做白名单校验，不合法直接拒
过度规划 一句话能做完的事拆成 15 步 设步数上限；简单任务走单步分支
粒度过粗 「分析一下数据」这种步骤无法执行 要求每步有明确的 action 和 done_when
计划漂移 跑到一半忘了目标，越走越远 每步回传目标摘要；重规划时重新注入 goal

模板在这里不是「代替模型思考」，而是承接已经确定的部分：格式、合规话术、金额单位、字段顺序。模型只在真正需要判断的地方生成——不是不让它生成，是不让它在已经有答案的地方自由发挥。

所以完整的分工是：

层 谁负责 解决什么
规划 模型 想清楚要做哪几步、用什么工具、怎么算完成
执行 模型 + 代码 按步骤做，每步的输入输出都过 schema
模板 代码 承接确定的部分，锁住格式和合规

一句话：规划负责「想清楚做什么」，schema 负责「把每一步做对」，模板负责「把确定的部分固化」。 三者是分工，不是替代。

3. 能力阶梯：从补全到自主

同样是「用 LLM」，复杂度可以差两个数量级。我把它分成六级，每上一级，增加的不只是模型能力，还有一整套基础设施：

层级 它做什么 典型形态 新增的基础设施 主要失败模式
L0 补全 给前缀，续写后续 IDE 里的 tab 补全 无 补出过时或不存在的 API
L1 单轮转换 一次指令，一次输出 翻译、抽取、分类、改写 一个 HTTP 调用 格式漂移、边界样本翻车
L2 多步推理 先想再答 数学题、代码生成、复杂判断 CoT / thinking budget 想错了但很自信、推理 token 烧钱
L3 外部知识 查了再答 RAG 问答、搜索、查库 检索 + 重排 + 引用校验 检索错 → 自信地错
L4 行动 做了再说 工具调用、Agent Loop 工具注册 + 权限 + 沙箱 + 循环控制 参数错、越权、注入、死循环
L5 自主 自己定目标、长时运行 编码 Agent、运营 Agent 状态机 + 记忆 + 人类闸门 目标漂移、成本失控

这张表最重要的用法是定位，不是分级炫耀。

客户说「我想要一个 AI 助手」，你先问两个问题：

  • 它需要知道公司内部的东西吗？→ 需要，就是 L3；
  • 它需要真的执行动作吗？→ 需要，就是 L4。

如果两个都不需要，那它就是个 L1 的文本处理——一个便宜的模型加一个 schema 就够了，别上 Agent 框架。

我见过最多的浪费，是用 L4 的基础设施去做 L1 的任务：为了「以后可能要做 Agent」，先搭一套工具注册、状态机、多 Agent 编排，结果核心业务只是把工单分成六类。框架的成本是提前支付的，而收益要等需求真的长到那一步。

反过来也有一类坑：明明是 L4 的任务（要查库存、要下单），却想用一个超长 prompt 一次搞定。这时候你缺的不是 prompt 技巧，是工具。

4. 一张按成熟度排的能力清单

下面这张清单不追求全，只追求能直接拿去做决策。我按「能不能直接上生产」分三档。

4.1 已经比人便宜且稳定（可以直接上，抽检即可）

能力 输入 → 输出 为什么稳 主要坑
分类 / 打标 / 意图识别 文本 → 枚举 输出空间小，可算 logprob 类别定义重叠；长尾类别样本少；否定句
字段抽取 文档 → JSON schema 可校验，可逐字段比对 长文档漏字段；单位/币种；条件和否定
常见语种翻译 文本 → 文本 语义等价，可回译校验 术语不一致；变量名/占位符被翻译；代码块被改
改写 / 润色 / 风格转换 文本 → 文本 原文就在上下文里 偷偷补充事实；改掉数字和专有名词
短文本摘要 文本 → 短文本 可逐句对照原文 丢否定词（「不建议」变「建议」）；丢条件
格式转换 结构 → 结构 输入输出同构 静默丢字段；注释和顺序丢失
代码解释 / 单测生成 代码 → 文本/代码 能跑就是验证 断言写反；编造不存在的 API
Embedding / 相似度 文本 → 向量 数值可计算 领域不匹配；长文本被截断

这一档的共同特征：输出形状是收敛的，或者有原文可以对照。 你不需要相信它，你只需要检查它。

4.2 能用，但必须带验证

能力 能用的前提 典型失败
长文档摘要 / 多文档综述 分段 + 引用回查 中间段落被忽略（lost in the middle）；多文档冲突被抹平
代码生成（多文件） 有测试、有类型检查 能跑但不符合项目约定；依赖幻觉；改坏上下文
写 SQL / 做数据分析 schema 喂全 + EXPLAIN + 只读账号试跑 理解错字段含义；join 错；聚合口径错
RAG 问答 强制引用 + 出处回查 检索不到就编；检索到了但原文不支持结论
结构化报告生成 数字全部来自工具，模型只写叙述 正文数字和表格对不上；结论和证据矛盾
多轮对话 显式状态 + 关键指令复述 长对话里忘掉 system 规则；状态漂移
文档 / 图像理解 关键字段二次校验 表格结构还原错；手写和低质扫描

这一档的特征是：模型能做出 80 分的初稿，但那 20 分必须由机器或人来补。 直接用的结果不是「差不多能用」，而是「错得很难发现」。

4.3 看起来能做，其实不要单独交给它

别单独交给它 症状 正确姿势
精确算术 / 计数 / 排序 「strawberry 有几个 r」答错；金额加错；排序漏项 让它写代码算，或直接调工具。数字永远不要经过模型的嘴
日期时间推理 「下下个周五」算错；跨时区错一天 模型只负责解析成结构化表达，计算交给 date 库
实时信息 不知道今天的股价、天气、新闻 搜索 / API，别指望参数里的记忆
私有数据 编造你公司的表名、字段、政策条款 RAG + 工具查询，并且要求「资料里没有就说没有」
高风险决策 医疗、法律、金融判断说得斩钉截铁 模型只给候选和依据，决策权在人
需要严格复现的任务 同样输入两次结果不同，回归测试没法做 结构化输出 + 断言 + 结果缓存，别指望 seed
长流程自主执行 20 步的任务跑到第 8 步就跑偏了 拆成短流程 + 状态机 + checkpoint + 人工闸门

这里面最容易被低估的是最后一条。下一节会算一笔账，你就知道为什么「20 步」是个很危险的数量级。

5. 五个判据：这件事到底能不能做

上面的清单是「别人做成了什么」，下面的判据是「你这个需求行不行」。拿到一个新需求，按顺序过一遍。

5.1 判据一：输出能不能定形？

这是最强的判据。问自己一句：我能不能用 TypeScript 类型把它写出来？

能定形，你就能校验、能重试、能算通过率、能做回归。不能定形，你连「对了没有」都说不清，更别说优化。

这一步做不好，后面所有工程手段都是白费。 因为验证器需要形状，评估需要标准答案，重试需要知道错在哪——这些都建立在「输出是可判定的」之上。

5.2 判据二：知识在不在？

模型的知识只有三个来源，判断需求时先归类：

来源 什么时候够用 典型问题
参数里（训练见过） 通用常识、编程语言、公开概念 版本更新后过时；长尾细节模糊
上下文里（你给的） 文档问答、代码 review、会议纪要 装不下；中间被忽略
工具里（现查） 数据库、内网 API、实时数据 要写工具、要权限、要控成本

一个反直觉但很有用的原则：

越是通用的知识，越该相信参数；越是具体的知识，越该相信工具。

问「什么是 TCP 三次握手」，不需要 RAG，模型记得比大多数人都清楚。问「我们 v2.3 的退款接口有哪些参数」，必须查文档——参数里那个版本大概率是错的。

判断方法很简单：问它一个只有你们公司知道的问题。 答「根据资料……」是 RAG 生效了；答得流利但具体细节全是编的，就是纯幻觉。

5.3 判据三：错了能不能被发现？

有验证器的任务和没验证器的任务，是两种完全不同的工程。

验证方式 适用 强度
能跑 代码、配置、正则 最强（布尔值）
能算 数字、金额、统计 强（可重算比对）
能查 引用、链接、数据库记录 强（存在性可判定）
能比 和原文/规则/另一个模型比 中（依赖比对器质量）
只能人审 文案、方案、语气 弱（成本高、不一致）

这里要说清一个区别：「没有验证器」不等于「不能做」，而是「不能自动化」。

这两个说法差别很大。「给客诉写一段安抚话术」没有验证器，但它可以做——生成三版，人选一版。而「自动给客诉定赔偿金额」没有验证器就不能自动做，因为没人愿意为错误兜底。

上一篇 4.3.3 给过一个公式，这里直接用：

把它简化成三档，判断会快很多：

错误代价 例子 策略
无副作用 推荐一句文案、生成一个标题 直接上，错了重来
可修改 回复草稿、代码建议、分析报告 人审一遍再发
不可逆 转账、删数据、对外发消息、下单 强制确认 + 权限最小化 + 幂等键

绝大多数线上事故，不是模型太笨，是把一个「不可逆」的动作放在了「无副作用」的策略里。判据一决定它能不能做，判据四决定它能不能自己做完——在不可逆的场景里，先问后者。

5.5 判据五：要几步？

这是最容易被低估的一条。

单步准确率 95% 听起来很好。但 Agent 是串行的，一步错，后面全错：

步数 端到端成功率（每步 95%） 端到端成功率（每步 99%）
1 95% 99%
3 86% 97%
5 77% 95%
10 60% 90%
20 36% 82%

而且这还是理想模型：假设每步独立、错误可恢复。真实的 Agent 里，错误会累积、会互相污染——第一步把「订单 A」认成了「订单 B」，后面所有查询都在为这个错误圆场（上一篇 4.1 ③ 的滚雪球）。实际衰减比这条曲线更快。

所以「能做」的边界往往不是能力边界，而是步数边界：

同一个模型，1 步能做的事，20 步就做不成。不是因为第 20 步更难，是因为前面 19 步总有一次会错。

这也是为什么「拆任务 + 每步验收」在 Agent 里不是架构美学，而是数学要求：你没法把单步的 0.95 变成 0.99，但可以在每一步之后检查，把错误挡在下一步之前。 20 步全对是 36%，可如果每步都能验证、失败能重试，端到端成功率就回到可用区间。

5.6 合成一张评分卡

把五条判据各打 0/1/2 分，加起来看结论：

维度 0 分 1 分 2 分
输出可定形 开放文本 半结构（Markdown/列表） schema 或枚举
知识可得 只能靠记忆 上下文能给全 工具能现查
错误可验证 只能人审 抽样比对 自动验证
错误代价 不可逆 可修改 无副作用
步数 > 10 步 3 ~ 10 步 1 ~ 2 步
总分 结论
8 ~ 10 可以直接做，重点在成本和体验
5 ~ 7 可以做，但必须配验证器或人审
0 ~ 4 别按原样做。要么缩小任务，要么改成「模型给候选、人来决策」

注意这里的分数不是「技术难度」，是「可控性」。高分不代表简单，代表错了你能兜住。

6. 能力放大器：同一个模型，四种用法

到这里，「模型本身能做什么」其实已经讲完了。但真实项目里，同一个模型能表现出的能力差距是数量级的——因为能力不全在模型里。

层 本质 补的是哪个缺陷 不解决什么
Prompt 改变条件分布 格式、风格、角色 它不知道的事实
RAG 往上下文里塞知识 知识截止、私有知识 推理能力、执行能力
Tool 把执行交给代码 算不准、做不到 该不该做（决策）
Agent 把规划 + 控制流交给模型 多步任务 单步可靠性

记住一句话：

RAG 不会让模型变聪明，它只是把答案放进了上下文；Tool 不会让模型变强，它只是把执行交给了代码；Agent 不会让模型变可靠，它只是把一次调用变成了 N 次调用。

所以每加一层，能力上限提高，不确定性也被同步放大。上一篇那句「Agent 工程的大部分设计，都是在给模型的缺陷打补丁」，说的就是这件事。

6.1 一个例子走完四层

需求：「帮我分析这个月退款率为什么上升。」

Prompt 版：它能给你一份很专业的原因清单——质量、物流、预期落差、季节性。看起来像模像样，但没有一个数字。这段话对任何人都成立，所以对谁都没用。

RAG 版：能引用公司的退款政策、历史复盘文档、上一次大促的结论。它会说「上次大促期间退货率上升主要因为尺码问题，参见 6 月复盘」。有依据了，但它不知道这个月发生了什么。

Tool 版：能真的跑 SQL——查退款率、按品类拆、按渠道拆、按退货原因拆。数字是真的，图表是真的。但它不知道下一步该查什么。

Agent 版：先查总览，发现女装品类异常，自己决定下钻到女装的退货原因，发现集中在某个 SKU，再查这个 SKU 的批次和供应商，最后输出结论。它自己决定了分析路径——先规划，再执行，中途还会根据观察结果改计划。

四层的能力差距是数量级的。但注意，失败模式也变了：

  • Prompt 版错了，你一眼看得出来（没有数字）；
  • Tool 版错了，你看不出来（数字是真的，但 SQL 的 join 写错了）；
  • Agent 版错了，你连它错在哪一步都不知道——所以必须有 trace。

这就是为什么「上 Agent」从来不是一个模型问题，而是一个可观测性问题。

6.2 每层新增的代价

层 延迟 成本 可观测性要求 失败半径
Prompt 1× 1× 看输出即可 一段话
RAG +100~300ms +检索 要看召回了什么 一个错误引用
Tool +工具耗时 +工具 +多轮 token 要看参数和返回值 一次错误写操作
Agent +N 轮 N 倍（且长尾） 必须有全链路 trace 一连串副作用

成本那一列要特别注意：Agent 的 token 消耗不是线性的，是长尾的。大部分任务 3 步结束，少数任务 40 步还在转——做预算时按 P95 算，不要按平均值。

7. 模型选型：选够用的，不是选最强的

7.1 三个约束

能力、成本、延迟，三者不可能同时最优。真实决策的顺序是：先定约束，再选模型。

先想清楚哪条是硬约束，剩下的空间其实很小。

7.2 按任务层级选

任务 建议档位 理由
分类 / 抽取 / 改写 小模型（mini / haiku 级） 输出空间小，大模型的边际收益很低
长文摘要 / 多文档 中模型 + 检索 需要覆盖面，不一定需要深推理
代码 / 多步分析 大模型或推理模型 需要中间过程
高风险判断 大模型 + 多次采样 + 验证 用钱换确定性

这里有个很常见的误区：用推理模型做分类。

它会在心里推演两千个 token，然后给你一个和 8B 小模型一样的答案——贵 20 倍，慢 5 倍。推理模型的价值在「需要探索解题路径」，不在于「知道答案」。分类、抽取、格式转换这类任务，思考过程是纯浪费。

反过来，让一个小模型去做「重构这个模块，保持所有测试通过」，也是浪费——不是浪费钱，是浪费你的时间。

7.3 成本结构怎么读

三条规则，看懂任何一家价目表：

  1. output 比 input 贵 3~5 倍。 因为 prefill 能并行，decode 不能（上一篇 2.3）。
  2. 缓存命中的 input 通常只收 10%~25%。 所以固定的 system prompt + 工具定义值得缓存。
  3. 推理 token 按 output 计费。 推理模型的账单经常比预估高 3~10 倍，就是这一项。

由此得到一张很实用的「贵不贵」判断表：

形态 典型场景 成本
长输入 + 短输出 分类、抽取、RAG 便宜
短输入 + 长输出 文案、生成 中
长输入 + 长输出 代码 Agent、长文分析 最贵

7.4 分层路由：把便宜的路走完

级联（cascade）是性价比最高的一招：

经济学很简单：如果 80% 的请求小模型能搞定，平均成本会降到原来的三分之一，而 P95 延迟只涨一点点——因为只有 20% 的请求走了第二档。

要注意的是：阈值必须校准过（上一篇 4.3.3 那张表），不能拍一个 0.9 就用。没校准的级联，要么全走小模型（质量崩），要么全走大模型（省了个寂寞）。

7.5 上下文不是越长越好

上一篇算过 KV Cache：8K 上下文差不多 1GB 显存。工程上还有另一个问题——lost in the middle：模型对开头和结尾的信息敏感，中间的内容容易被忽略。

所以「把 200 页文档全塞进去」通常不如「检索出最相关的 5 页」。前者更贵、更慢，而且准确率往往更低。

8. 别问「能不能」，问「通过率多少」

8.1 demo 和生产的差距，是一个乘法

一个任务单步 95%，听起来可以上线。但用户感知的是整个任务：

10 步就是 60%。这意味着 10 个用户里有 4 个失败——而你在 demo 里一次都没见过，因为你只跑了 5 次，5 次都成功。

这不是模型的问题，是概率的问题。要判断能不能做，你必须知道分布，而分布只能靠评测集。

（这也是规划真正的价值：它不能提高单步准确率，但能在每一步之间插一个检查点，把「一次错到底」变成「错了就停」。代价是更多轮调用、更长延迟，以及一个必须被设计好的重试/重规划策略。）

8.2 最小可用的 eval（50 行就够）

别一上来就搭评测平台。先做一张表：

  1. 抽 50~100 条真实样本，覆盖：典型、边界、已知难例、脏数据；
  2. 人工标注正确答案——这一步不能省，也不能让模型标；
  3. 跑一遍，记录：对/错、失败类型、延迟、token；
  4. 只看两件事：通过率、失败模式分布。

（normalize 要先想清楚：大小写、空格、数字格式、同义词。归一化写错，评测结果全是噪音。）

8.3 看三个数

指标 回答什么问题 怎么用
通过率 能不能上 低于业务底线就换方案
失败模式分布 该补什么 决定加规则、加检索还是加人审
单次成本 / P95 延迟 值不值得上 决定模型档位和缓存策略

真实的分桶结果大概长这样：

分桶 样本 通过率 主要失败模式
常规工单 42 95% —
含否定句 18 61% 把「不需要退款」抽成「退款」
多订单 12 50% 只抽到第一个订单号
中英混合 8 88% 类别返回英文枚举

这张表比一个总分有用得多。总分 78% 说明不能直接上；但分桶告诉你：只要加一条「否定词检测 + 多订单拆分」的前处理，最烂的两桶就能拉起来。

评测的价值不在分数，在于告诉你下一步改哪里。

顺带说一句：这也是为什么「感觉这个模型变强了」不可信。模型会静默更新（system_fingerprint 变了），你的 prompt 会改，线上数据分布会漂。没有 eval，你连回归都发现不了。

9. 一次完整判断：把需求拆到子任务

拿一个真实需求走一遍。

需求：客服工单自动处理。

第一步不是选模型，是拆子任务。每个子任务单独判级：

子任务 动作 / 层级 验证方式 方案 人审
意图分类 决策 / L1 6 类枚举 + logprob 小模型 + 阈值 否
订单号抽取 抽取 / L1 schema + 查库存在性 小模型 + 正则兜底 否
紧急度判断 决策 / L1 3 档枚举，抽样 小模型 否
查订单状态 工具 / L4 参数 schema + 返回校验 只读 API 否
生成回复草稿 生成 / L2 只能人审 大模型填槽 是
是否升级人工 决策 / L2 布尔，规则优先 规则 + 模型兜底 否

结论很清楚：6 个子任务里 5 个能自动跑，只有「回复草稿」需要人审——而它恰好是最像「AI」的那个。

这就是真实项目的样子：AI 的含量比 demo 低，但可用性比 demo 高得多。

这里要分清一件事：上面这张表是我们（工程师）先拆的，不是让模型临场拆的。 真实运行时有两种做法：

  • 路径固定的部分（查订单、是否升级）直接固化成 workflow，模型只负责填参数；
  • 路径不固定的部分（该查哪张表、要不要下钻、异常怎么解释）才交给模型规划。

能固化的流程不要交给模型规划。 规划的价值在「不知道该走哪条路」的时候；路径已知还让模型规划，只是多花一次调用，还多一个出错的环节。

再往前一步。如果需求变成「自动退款」呢？

多了一条硬约束：涉及资金、不可逆。判据四直接否决自动执行，方案改成「模型生成退款单，人点确认」。这不是技术做不到，是风险不接受。

能区分「技术做不到」和「风险不接受」，基本就具备做 Agent 的判断力了。

10. 小结

如果这篇只记五句话，我希望是这五句：

  1. 它只会生成 token。 所有「做事」都是你的代码替它做的。所以能力边界 = 你能把动作写成函数的边界。
  2. 工程分两层：任务级先规划，步骤级收敛输出。 复杂任务让模型先出计划、按步执行、随时重规划；每一步再用 schema / 枚举把输出锁死。模板承接确定的部分，不是替代生成。
  3. 五个判据：能不能定形、知识在不在、错了能不能发现、代价多大、要几步。 其中「步数」是指数衰减的——20 步就是 36%，这不是能力问题，是数学。
  4. RAG / Tool / Agent 都是放大器，不是聪明药。 每加一层，能力上限和不确定性一起涨。加之前先问：我补的是哪个缺陷？
  5. 别问「能不能做」，问「在多少条样本上、多少通过率、多少成本、几步以内」。 没有 eval 的「能做」，本身就是一种幻觉。

下一篇先插一篇实战：LLM 的实际使用例子（LangChain）——从一次最简单的模型调用开始，到 Prompt 模板、结构化输出、工具绑定、链式编排，最后拼出一个能查数据、能调工具的小 Agent。也会顺带看看：哪些事框架替你做了，哪些事它其实没做、还得你自己兜。
